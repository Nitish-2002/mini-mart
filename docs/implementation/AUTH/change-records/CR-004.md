# CR-004 — Session delivery must be httpOnly-cookie-only, not also echoed in the JSON response body, to actually get decision-35's XSS protection

**Date:** 2026-09-04
**Tasks affected:** inferred: see ## Change Summary
**Raised by:** Bhargav
**Tier:** design

## What was specified

Two things, both already approved, that contradict each other. [system-architecture.md's Permission Model](../../../system-architecture.md#permission-model-and-governance) (decision-35): "AUTH_SERVICE issues a JWT... stored in an httpOnly cookie, so the frontend never handles the raw token in JavaScript." Separately, [trd.md's API Contracts](../trd.md#api-contracts) and [experience-design.md's Mock Contracts](../experience-design.md#mock-contracts-and-data) both document `otp/verify`, `admin/login`, and `admin/password-reset/confirm` as returning `session_token` as a plain JSON response field.

## What reality showed

Implementing TASK-AUTH-012 (the authorization dependency) surfaced the contradiction directly: an httpOnly cookie's entire security property is that `document.cookie`/JS can't read it, so an XSS payload can't steal it directly. But if the same token is *also* returned in the JSON response body of the request that sets it, any JS running on the page — including an XSS payload — can read the token straight out of the `fetch()` response, regardless of the cookie's `httpOnly` flag. Documenting the token as a body field, as trd.md and experience-design.md currently do, silently defeats decision-35's entire stated purpose.

## Impact

As specced, every session-issuing endpoint would ship with no real XSS protection despite `system-architecture.md` explicitly claiming it has one — a security posture gap that's invisible until someone reads both documents side by side, exactly what happened here. [TASK-AUTH-007](../tasks.md#task-auth-007-otp-verify-and-session-issuance)'s already-implemented code returns `session_token` in the body, matching the old (wrong) contract, and needs to change.

## Proposed resolution

Session issuance sets a real httpOnly cookie (`Set-Cookie: session_token=...; HttpOnly; Secure; SameSite=Lax; Max-Age=...`) and the JSON response body drops `session_token` entirely — only `role` and `expires_at` remain (still useful to the frontend for UI state, and readable by JS since they aren't secrets). Applies to all three session-issuing endpoints: `otp/verify`, `admin/login`, `admin/password-reset/confirm`. `logout` (TASK-AUTH-013 in trd.md's numbering) clears the same cookie via `Set-Cookie` with an expired `Max-Age`, not a body field either.
