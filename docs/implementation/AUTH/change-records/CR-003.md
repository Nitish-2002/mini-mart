# CR-003 — TRD never tagged its testable technical requirements with TRD-AUTH-NNN IDs, blocking 50b's traceability table

**Date:** 2026-09-04
**Tasks affected:** inferred: see ## Change Summary
**Raised by:** Bhargav
**Tier:** trd

## What was specified

Stage 50a's own output list, item 1, requires: "Assign `TRD-[MODULE]-NNN` to every testable technical requirement." [trd.md](../trd.md) was approved without ever assigning a single `TRD-AUTH-NNN` ID — its testable technical requirements exist only as prose inside Decision/Invariant summaries and section text (e.g. `decision-68`'s Argon2id choice, `inv-auth-singleton-admin`'s singleton constraint), with no stable, independently-citable requirement ID a Test case can point at.

## What reality showed

Starting stage 50b (Test Specification) surfaced the gap directly: stage 50b's own CONTEXT requires a traceability table mapping every `SS-[MODULE]-NNN`, `SY-[MODULE]-NNN`, **and testable `TRD-[MODULE]-NNN`** to one or more `TEST-[MODULE]-NNN` IDs — and "a requirement without a Test mapping blocks approval." With no `TRD-AUTH-NNN` IDs to map against, the Test Specification would either have to invent IDs unilaterally (silently patching an approved doc) or skip TRD-level traceability outright (a real coverage gap the gate is specifically designed to catch).

## Impact

Without this fix, stage 50b either can't be approved cleanly (missing traceability) or gets built on IDs invented ad hoc outside the change process, which is exactly the kind of drift Daksh's gates exist to prevent. No business flow, system behavior, or technical decision changes — every requirement below already exists in `trd.md`'s prose; this only assigns it a stable, citable ID.

## Proposed resolution

Add 15 `TRD-AUTH-NNN` ID tags to already-written testable technical requirements across `trd.md`'s Data Model, 5a, 5b, API Contracts, and Security Design sections — each tag placed inline next to the existing sentence it labels, with no change to any decision, schema, or contract already approved. `docs/implementation/AUTH/tasks.md` does not exist yet (this module hasn't reached stage 50c), so the change-task skeleton `change.py` looked for could not be written to disk — noted, not a blocker for this CR.
