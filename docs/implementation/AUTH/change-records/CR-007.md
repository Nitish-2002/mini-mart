# CR-007 — FRONTEND_AGENT's routes were never namespaced, colliding with FRONTEND_STOREFRONT's identical bare paths in the same one-deployable app

**Date:** 2026-09-04
**Tasks affected:** inferred: see ## Change Summary
**Raised by:** Bhargav
**Tier:** design

## What was specified

[experience-design.md's Information Architecture](../experience-design.md#information-architecture-and-navigation) opens by calling AUTH's three roles "three separate frontend applications," then gives `FRONTEND_STOREFRONT` bare paths (`/login`, `/login/verify`) and `FRONTEND_AGENT` its own bare paths (`/register`, `/status`, and — critically — the *same* `/login`/`/login/verify` paths as `FRONTEND_STOREFRONT` for an approved agent's login).

## What reality showed

Scaffolding the real Next.js project (TASK-AUTH-013) surfaced the contradiction: [system-architecture.md's Frontend Architecture](../../../system-architecture.md#frontend-architecture) already fixed this as "**one deployable** serving three role-scoped route groups... **rather than three separate applications**," and its own Permission Model gives the concrete mechanism — "a request to `/admin/*` without an `admin` claim is rejected," i.e. role is distinguished **by URL path prefix** within the one app, not by which separate domain/app was opened. `FRONTEND_ADMIN`'s `/admin/*` prefix already follows this correctly. `FRONTEND_AGENT` never got an equivalent prefix, so its routes are identical strings to `FRONTEND_STOREFRONT`'s in the same Next.js router — not merely a documentation error, a real routing collision that makes the two role experiences literally unbuildable as written.

## Impact

As specced, `/login` cannot simultaneously belong to two different pages in one Next.js app. Building it literally would mean one of the two roles silently loses its login page. This blocks TASK-AUTH-013 and TASK-AUTH-014 from proceeding correctly.

## Proposed resolution

Prefix every `FRONTEND_AGENT` route with `/agent`, mirroring `FRONTEND_ADMIN`'s `/admin` prefix exactly: `/agent/register`, `/agent/register/submitted`, `/agent/status`, `/agent/login`, `/agent/login/verify`. Correct the opening paragraph's "three separate frontend applications" to match architecture's actual "one deployable, three route groups" framing — the app-boundary-decides-role mechanism from [decision-49](../solution.md#business-states-decisions-and-recovery) is realized via the URL prefix, not a separate domain/app. No screen, component, or interaction changes — [ds-auth-001](../experience-design.md#4c-design-execution)/[002](../experience-design.md#4c-design-execution) are still the same reused screens for both roles, just served at two different path prefixes instead of one shared path.

## Change Summary

### Changes to `docs/implementation/AUTH/experience-design.md`
- §Information Architecture and Navigation, opening paragraph: correct "three separate frontend applications" to "three role-scoped route groups within one deployable," matching system-architecture.md's own wording exactly.
- §FRONTEND_AGENT route list: add the `/agent` prefix to every route (`/agent/register`, `/agent/register/submitted`, `/agent/status`, `/agent/login`, `/agent/login/verify`); correct the "routed to `/login` → `/login/verify`, the same two routes... as End User" sentence to say `/agent/login` → `/agent/login/verify` — the same reused *screens/components*, not the same *URL* as End User's.

No changes to `solution.md`, `system.md`, `trd.md`, `business-requirements.md`, `implementation-roadmap.md`, `vision.md`, or `client-context.md` — purely a routing-namespace correction inside the design spec, no business flow or system behavior changes.
