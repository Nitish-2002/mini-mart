# CR-005 — trd.md never documented an endpoint for Admin's agent approve/reject/deactivate/reactivate actions

**Date:** 2026-09-04
**Tasks affected:** inferred: see ## Change Summary
**Raised by:** Bhargav
**Tier:** trd

## What was specified

[system.md](../system.md#logical-interfaces-and-data-flow) defines `interface-auth-agent-mgmt` as covering both halves of the agent lifecycle: "registration details in -> pending record out; admin decision in -> updated agent status out." [trd.md's API Contracts](../trd.md#api-contracts) table lists 8 endpoints under this interface's identity/agent/admin groupings, but only one of them — `POST /v1/auth/agent/register` — actually belongs to `interface-auth-agent-mgmt`. No endpoint for the "admin decision in" half exists anywhere in the document.

## What reality showed

Starting [TASK-AUTH-009](../tasks.md#task-auth-009-agent-lifecycle-actions-and-audit-log) (Admin's approve/reject/deactivate/reactivate actions) surfaced this directly: there is no documented contract to implement against. [5b State Machines](../trd.md#5b-state-machines) fixes the four valid transitions precisely (`pending_approval->approved`, `pending_approval->rejected`, `approved->deactivated`, `deactivated->approved`) and states each one "update `auth_delivery_agents.status`, insert one `auth_agent_status_log` row — same transaction," but never says what HTTP call triggers it. Per this stage's own TRD contract gate ("Tasks implementing an API or message contract require the corresponding Interface to have a formal schema artifact... If a required TRD section is missing or hand-wavy, do not emit the task. Instead, emit a contract-hardening task against the TRD itself"), this should have blocked TASK-AUTH-009 from being written as a ready-to-implement Story in the first place — it wasn't caught at Tasks-stage time.

## Impact

Without a fixed contract, implementing TASK-AUTH-009 would mean inventing the endpoint shape silently inside a code PR, with no doc anyone could review it against — exactly what the TRD contract gate exists to prevent. No business flow or system behavior changes; [5b](../trd.md#5b-state-machines)'s transition table is already correct and unaffected — this only adds the missing transport contract around it.

## Proposed resolution

Add `POST /v1/auth/agent/{agent_id}/status` to trd.md's API Contracts: admin-only (`require_role("admin")`), body `{"action": "approve" | "reject" | "deactivate" | "reactivate"}`, success `200 {"status": "<new_status>"}`. Errors: `404` if `agent_id` doesn't exist; `409 invalid_transition` if the requested action isn't valid from the agent's current status (e.g. `approve` on an already-`approved` agent) — rejecting any transition not in [5b](../trd.md#5b-state-machines)'s closed table, per TASK-AUTH-009's own decision budget ("any transition not in sm-auth-agent-status's table must be rejected"). One endpoint with an action enum, not four separate endpoints — TASK-AUTH-009's decision budget explicitly left this choice to the implementer; one endpoint keeps the closed-transition-table validation in one place instead of duplicated four ways.

## Change Summary

### Changes to `docs/implementation/AUTH/trd.md`

- §API Contracts overview table: add the new endpoint row (method, consumer `FRONTEND_ADMIN`, auth required `Session (admin)`).
- §5b State Machines (agent status machine's transition table): add a one-line pointer from the transition table to the new endpoint, so a reader lands on the concrete contract from the abstract transition list.

No changes to `solution.md`, `system.md`, `experience-design.md`, `business-requirements.md`, `implementation-roadmap.md`, `vision.md`, or `client-context.md` — no business flow or system behavior changes, only a missing transport contract added. Ascent stops at trd.md.
