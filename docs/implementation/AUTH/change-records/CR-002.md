# CR-002 � OTP request/verify need a role discriminator to resolve End User vs Delivery Agent identity under a shared email

**Date:** 2026-09-04
**Tasks affected:** inferred: see ## Change Summary
**Raised by:** Bhargav
**Tier:** system

## What was specified

[system.md](../system.md#logical-data-ownership-and-invariants)'s `dm-otpcode` shape is "hashed code, associated email, issued-at timestamp, expiry (10 minutes), consumed flag" — no field distinguishing which role (End User vs Delivery Agent) the code was requested for. [experience-design.md](../experience-design.md#mock-contracts-and-data)'s mock contract mirrors that: `POST /v1/auth/otp/request` takes `{ "email": "..." }` and `POST /v1/auth/otp/verify` takes `{ "email": "...", "code": "..." }` — email and code only, no role.

## What reality showed

Drafting the AUTH TRD's concrete data model and API contracts surfaced a real gap: [decision-49](../solution.md#business-states-decisions-and-recovery) (solution.md) lets the same email hold both an End User and a Delivery Agent identity as two separate account records. [experience-design.md](../experience-design.md#information-architecture-and-navigation)'s own Information Architecture puts End User and Delivery Agent in two separate frontend apps (`FRONTEND_STOREFRONT`, `FRONTEND_AGENT`) that both call the same shared `interface-auth-identity` mechanism ([ss-auth-001](../solution.md#business-flow-inventory)). With only email+code in the request, the backend has no way to know which of the (possibly two) identities under that email a given OTP request or verify is for — it cannot pick which record to create/check, or which role to embed in the issued session's claim ([decision-35](../../../system-architecture.md#permission-model-and-governance)).

## Impact

Without this field, `POST /v1/auth/otp/verify` is ambiguous for any email that holds both identities: the backend cannot deterministically resolve which role's session to issue. Left unfixed, this would either force an undocumented, ad hoc resolution rule invented silently in the TRD (violating the flow-back rule) or block AUTH's TRD from being written at all, since [interface-auth-identity](../system.md#logical-interfaces-and-data-flow)'s shape can't be finalized without it. This does not change any business flow, screen, or already-decided threshold ([decision-49](../solution.md#business-states-decisions-and-recovery), [decision-50](../solution.md#business-states-decisions-and-recovery), [decision-53](../solution.md#business-states-decisions-and-recovery) all stand unchanged) — it is a payload-shape gap, not a new capability.

## Proposed resolution

Add a `role` field (`"end_user"` | `"delivery_agent"` — reusing the exact role vocabulary [system-architecture.md](../../../system-architecture.md#permission-model-and-governance) already fixed for the JWT claim, not a new term) to both `POST /v1/auth/otp/request` and `POST /v1/auth/otp/verify`. The frontend already knows which value to send without any new UI: it's implicit in which of the two separate frontend apps ([Information Architecture](../experience-design.md#information-architecture-and-navigation)) is making the call, so no screen, copy, or interaction changes — only the two request payload shapes in the mock contract, and `dm-otpcode`'s shape in system.md. The 5-per-hour OTP rate limit ([decision-53](../solution.md#business-states-decisions-and-recovery)) stays scoped to the email alone, shared across both roles, matching its existing wording exactly ("5 requests per hour per email") — this CR does not touch that decision.

## Change Summary

### Changes to `docs/implementation/AUTH/system.md`
- §Logical Data, Ownership, and Invariants / `dm-otpcode` node: extend `shape` to include the `role` field, tied to one email **and role**, not just one email.
- §Logical Interfaces and Data Flow / `interface-auth-identity` node: extend `shape` to show `role` as part of the request shape for both the request and verify legs.

### Changes to `docs/implementation/AUTH/experience-design.md`
- §Mock Contracts and Data: add `"role": "end_user" | "delivery_agent"` to the `POST /v1/auth/otp/request` and `POST /v1/auth/otp/verify` request examples, with a one-line note that the value is implicit per frontend app, not a new UI field.

No changes to `solution.md`, `business-requirements.md`, `implementation-roadmap.md`, `vision.md`, or `client-context.md` — this doesn't change a business flow, decision, or scope boundary, only a data/interface shape one level below where those documents operate. Ascent stops at system.md.
